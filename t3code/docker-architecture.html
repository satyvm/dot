T3 Code / architecture decision / 2026-09-24

Keep Docker off the Coolify host

T3 Code runs on an Oracle-hosted Coolify stack. Its agents need build-and-test capacity, but granting the production host's Docker socket would also grant control over production containers. The chosen path is a native Docker SSH context to a dedicated builder, carried through the Tailscale sidecar's SOCKS5 proxy.

01 — Current repository stack

The T3 application and Tailscale sidecar share one network namespace. T3 serves the browser UI through Tailscale Serve; the Coolify host publishes only the sidecar's UDP transport. There is deliberately no Docker daemon or host socket inside T3.

03 — Chosen extension

T3 stays on Oracle. A separate persistent VM owns Docker Engine, build cache, containers, and test volumes. Only OpenSSH is reachable from tag:t3 over the tailnet; the Docker API itself remains on the builder's Unix socket.

04 — Operational contract

What persists where

T3 keeps agent state, SSH identity, Docker context metadata, and source checkout in its home/workspace volumes. The builder keeps image layers, build cache, test containers, and named volumes.

How a build works

Compose reads the project on T3 and sends the build context over SSH. A build can therefore use local uncommitted changes without a sync wrapper.

How a run works

Bind-mount host paths and published ports resolve on the builder. Use named volumes or a checkout on the builder for bind-heavy integration tests.

Security boundary

Docker group membership is root-equivalent on the builder. Isolate it from production, restrict the tailnet grant to TCP 22, and never publish Docker's daemon API.
